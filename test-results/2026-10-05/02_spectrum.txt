SPECTRUM SCALE FACTORS BEFORE AND AFTER sdt analyze
====================================================

RESULT: the suspected bug is confirmed.
With kN-m as the units the API works in, sdt analyze wrote 1153.7235 as the scale
factor of every response spectrum case. In kN-m that is 1153.72 m/s2, 1000 times
g I / R (1.1537 m/s2). The RSA base shear became 541,024 kN against a static base
shear of 682 kN (793 x), the scaling step left it alone (scale up only), and
sdt analyze reported no warning. With N-mm units the same model gives 1153.72
mm/s2, then scales RSAX x 1.261 and RSAY x 1.228 to reach 100 % of the static shear.

IMPORTANT, about 'a model in kN-m units'
----------------------------------------
The only model on this machine has N-mm as its database units (it was made by
sdt setup). I could not make a copy whose database units are kN-m: ETABS fixes
them when the model is created, and the .$et text file is always written in the
database units. What was done instead: SapModel.SetPresentUnits(6) (kN-m) on the
copy before running the command. Present units are what the API reads and writes
in, so this reproduces what the code sees on a kN-m model, but it is not a model
created in kN-m. Two things seen while doing it:
  - Present units belong to the ETABS session, not to the file. A new ETABS that
    opens the copy saved with kN-m present units reports N-mm again (the database
    units). Opening another model in the same session keeps the kN-m.
  - So the value sdt writes is interpreted in whatever units the session is in at
    that moment. A model created in kN-m opens with kN-m present units, and so
    would hit this every time.
Not checked: whether the units box at the bottom right of the ETABS window is the
same setting as the API's present units (the runs had no one at the screen).

Scale factors are listed three ways: as the API returns them in the present units,
and converted by ETABS to N-mm and to kN-m. I and R are in the pattern table.
